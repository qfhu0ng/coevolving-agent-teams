| 机制 | 规则 | 作用范围 | 后果 | 代码位置 |

上面前三条不受 `skipLoopDetection` 影响。触发之后：

- **master 或 Single**：主 CLI 退出。master 退出时，退出清理会取消所有 worker（诊断记录引用 `llm-UDFWQWZA.js:3319`、`chunk-PDUMGZ2P.js:163910`）。
- **worker**：当前 `runOneRound` 返回 `LOOP_DETECTED` 并记录错误；原生仍可能先处理已排队的下一条消息，队列耗尽且错误仍在时变为 FAILED。不是检测瞬间无条件杀全队；终态失败后由现有失败通知路径告知 master（`chunk-PDUMGZ2P.js:78834, 78980`）。

每回合计数不是每次 API 请求计数，也不是 worker 一生的总数：工具续轮共享计数，新的 `runOneRound` 重新创建检测器；`between_tool_calls` 插入的消息不重置当前回合计数。`task_list` 的重复信号按返回结果处理，不能机械套用普通工具的累计 6 次。调用计数包含送入检测器的请求，不等于成功执行次数。显式设置 500 会变成硬上限，未必比默认最多允许 1000 次有差异调用更宽松。

**原生的等待方式**（`chunk-TWAMIEQ2.js:1787–1815`）：

- master 不调用工具、结束回合后，只要还有队友在工作，就循环 `waitForTeammateActivity`，每 120 秒检查一次，等待期间不调用模型。
- 队友消息或 check-in 到达时，master 被唤醒。
- worker 结束回合时，原生会自动给 master 发一条完成通知（`reportFinalAnswer`）。

**全员停滞**：master 进入原生等待路径后，如果所有剩余非终态 worker 都达到 `STALL_THRESHOLD_S` 的无活动条件，会终止它们。本轮实际门槛是 2040 秒（34 分钟），由 `qwen.py:236–245` 与 `qwen_stall_timeout.mjs` 设置。长命令且没有被记录的活动是可能情形，不是唯一原因；不能把模型上游仍在流式响应等同于 TeamManager 收到活动事件。

**我们自己的设置**：

- check-in 每 1800 秒一次，另在 50%、75% 两个节点各一次；状态文件约每 60 秒刷新。
- master 提示里写着"需要时用 `read_file` 读状态文件"（`agent_company/runtime/qwen.py:126`），但没有说怎么等待，也没有说上面这些保护规则。

## 4. 原因判断

- **直接原因**：master 的轮询触发了连续相同调用保护，主 CLI 退出。这是已证实的事实。
- **框架缺陷**：
  1. 没告诉 master 结束回合就是在等，会被消息、自动通知或 check-in 唤醒；
  2. 提示主动建议读状态文件，却没有明确其刷新周期和原生等待的配合方式。它不是唯一的信息来源：队友消息、任务板和 check-in 都存在；尚未证明其他时间获取路径都不可用；
  3. 保护规则没有向 agent 和 optimizer 披露；
  4. master 的一次失误会让整个团队终止。
- **诱因（解释，未验证因果）**：P1 要求按时间比例检查、以交付仓库为准，使 master 需要随时掌握时间和交付状态。
- **定性**：本次是策略行为、运行时接口与保护后果发生交互的事故；不能据此单独判定 P1 策略效果，也不能反向断言 P1 无影响。当前框架提示未明确披露这些限制，不等于能证明 optimizer 的内部认知。已证实的修复需求是合法等待接口说明不足，以及此类轮询被放大成全队退出。

## 5. 修复方案

### 5.1 第一步：讲清楚等待方式和保护规则

这一步说明运行环境，不替 optimizer 决定策略，但仍会改变模型可见输入和运行条件。A/C 原文不动；角色提示按实际能力分别披露，不能教 Single 用不存在的 Team 等待能力。

- **master 提示**（check-in 说明处）：
  - 没有可执行的协调动作时，结束当前回合即可等待；
  - 队友消息、worker 结束回合时的自动通知、check-in 都会唤醒你；
  - 唤醒时间表：check-in 每 30 分钟一次，外加 50%、75% 两个节点；
  - 状态快照约每分钟刷新，不需要持续读取。
- **保护规则披露**：master、worker、Single 各自写明实际生效的规则——连续 5 次相同调用、每回合上限、连续 8 次 git 查看（只对能跑 shell 的角色），以及触发后的后果。
- **状态文件开头**加运行时说明字段，写明刷新间隔和等待方式。字段形式是数据，但模型读取后仍是模型可见输入，不能以“不是系统提示”为由当作实验条件不变。
- **optimizer 和 reviewer 的背景**：在证据投影里加入同样的运行时事实（唤醒时间表、保护规则），和现有的提交规则并列，让后续策略能据此设计检查点。
- **不写**"不要冻结""改用事件检查"之类的结论。检查点怎么设，由 optimizer 决定。

拟修改位置为 `qwen.py` 中按角色生成的运行时说明、已有 relay worker-system-note 注入路径、check-in 快照构造，以及证据投影的运行时事实字段；这只是范围清单，不授权此刻修改。唤醒时间表应来自实际配置，并说明排队、合并、收尾期间暂停发送等边界，不能承诺准点必送。worker 在一轮内部接收消息并不等于原生结束回合。

建议披露与恢复分成两个独立 opt-in 设置，默认关闭，实际值写入已有运行设置/launch。披露关闭时旧角色提示与旧快照字段保持不变；恢复关闭时旧保护后果保持不变。开启的运行时事实同步进入供 optimizer/reviewer 使用的投影，并写明实际生效值；旧记录缺字段视为未知，不补成新机制已开启。不另建冻结合同或重复的版本登记体系。

### 5.2 第二步：master 触发保护后的受限恢复

目标：
> 拦下这次调用 → 安全结束 master 当前回合 → 保留 worker，进入原生等待 → 有消息或 check-in 时继续协调。

不采用"返回错误后立刻再请求模型"，那样容易变成持续花钱的循环。

**触发范围（推荐 A，仍待用户确认）**：

| 选项 | 覆盖范围 | 好处 | 风险 |
|---|---|---|---|
| A（窄） | 仅 Team master、`consecutive_identical_tool_calls`、只读 `read_file` 且目标为本次 runtime 的精确状态文件路径 | 有本次事故和机制复现作为依据；其他保护不变 | 别的循环仍可能令主 CLI 退出 |
| B（宽，本轮不建议） | master 遇到任何常驻循环保护都转等待 | 可能覆盖其他未来故障 | 没有逐类可恢复性证据，可能掩盖无进展循环并改变每回合预算含义；有 worker 存活本身不构成安全证明 |

本轮不预设“累计 N=3 后终止”。三个相隔很久、期间有真实进展的独立轮询事件不应仅因累计次数被直接认定同一死循环。先复用既有六小时期限、取消、全员停滞和原生消息等待，禁止无消息时立即重问模型。若脚本复现证明现有边界仍允许不可接受的重复恢复，再明确该情景、连续性/进展定义和重置规则，提出有证据的限制；不能仅为宽泛恢复新增任意门槛。

**行为细节**：

- 被拦下的读取不执行。必须核对本轮整个工具批次：触发前同批其他调用可能已传给外层但尚未执行，不能只给第五条补结果，也不能悄悄执行、丢弃或重放其他工具。对已记录但未执行的调用，按真实状态补取消/未执行结果，每个调用恰好配对一次；不伪造成功或新文件内容。首版只恢复可证明为纯目标状态读取的批次，混合其他工具的批次保持原生失败；仍需验证失败侧历史和执行状态不被误改。
- 区分 active、idle、terminal：`hasActiveTeammates()` 为 false 也可能是全员 idle，不能当作全员死亡或完成。首版要求有 active worker 才进入该恢复路径；触发时只有 idle 或全部 terminal 则保留原生失败，不伪装成功。等待期间 active→idle/terminal 的竞态必须保留最终 inbox drain，利用真实终态/完成通知进入正常收尾；若无法安全完成交接，保留失败，不盲目等或自动成功。
- 进入等待不是清标志后马上重发旧 toolResult。core 与 runner 都有持续置位的保护状态，需结束旧协调段，在原生消息开启下一 interaction 时正确重置；不续借旧段预算，不伪造 worker 活动。
- 120 秒 wait timeout 或状态文件时间戳刷新不会主动产生新模型请求；真正到达的队友消息/check-in 沿既有路径唤醒。恢复次数作为观测指标，不先作为全队终止门槛。观测注明触发类型、角色、时间、进入等待/唤醒及终止原因，不保存推理正文或新复制整段消息。
- 其他情况仍走原生处理：worker 自己的保护（单人失败、不连累全队）、执行错误、安全拒绝、6 小时期限、用户停止、全员停滞。

**实现**：

- 至少核对两处落点：core 检测点（`chunk-PDUMGZ2P.js:92729`）在触发调用未 yield、待执行列表被清空之前提供窄范围识别依据和批次状态；无人值守 runner 将该可恢复事件转入现有等待，而不执行 `emitLoopDetectedResult()`。只改 runner 不足以可靠辨认目标文件，因为当前 loop 事件只带类型。
- 沿用现有 opt-in 兼容层及其不兼容时拒绝应用补丁的行为，不修改服务器安装包。恢复开关独立于披露开关，默认关闭；记录到已有 `launch.json` 和运行设置。
- 难点：保护通过事件返回，并会清掉待执行的工具调用，需要正确处理调用记录、结果配对和检测状态。不是加一层 `try/catch` 就够。

### 5.3 第三步：每回合上限先不改

- 不显式设置 `maxToolCallsPerTurn`，避免它变成硬上限。
- 先加观测：按原生回合边界记录 worker/主会话调用计数、重复信号、重置/重试事件和触发类型，仅记元数据。明确是检测器看到的工具请求数，不是 API 次数或成功执行数；统计不得改变计数、历史和模型输入。
- 等有证据表明正常工作会撞上，再讨论调整方式。

### 5.4 暂不做

- 修改 P1 的分工、通信或冻结规则。
- 全局关闭循环保护。
- "预约在某个时间点唤醒"这项新能力：尚未证明现有消息/check-in 对所有时间检查点都足够，也没有证据要求本轮新增调度器；先验证既有路径。披露当前能力，不人为改写 P1 的时间检查策略。

## 6. 验证计划

### 9.2 与第 5 节的差异（按实现时核对的原生事实）

1. **首版只恢复"整条回复只有这一次状态读取"**。若同一回复里还有别的调用（包括另一条相同读取），记录 `other_calls_in_response` 并保持原生失败。理由：被拦下的那条回复整体不进历史、其中调用都不执行；更早已交给 runner 的同批调用若继续回合会被执行，首版不处理。
2. **新核实：master 的计数在每次收到队友消息或 check-in 时清零**，包括随工具结果在回合中途送达的情况（这类请求以 `teammate` 类型开启新 interaction，`chunk-TWAMIEQ2.js:1600–1612`、`chunk-PDUMGZ2P.js:92125`）。master 在工作时到达的消息随下一批工具结果送达，不是等到下一回合。披露文字按此写。
3. **新核实（风险，未处理）：Single 整个任务通常只有一个 interaction**，每回合计数横跨全程：超过 100 次工具调用后，任何一个完全相同的调用累计 6 次就会叫停整个运行，或累计超过 1000 次。worker 同样受这些上限约束：它的一轮从收到一条消息或任务开始，到回答且不再调用工具为止，可能持续数小时，工具之间收到的消息（`between_tool_calls`）不清零；区别只在后果——worker 被叫停只结束它自己这一轮，不终止全队。本次只披露，不改上限；重跑 P1 前需知晓。
4. 5.3 的"按原生回合边界记录调用计数"未实现。恢复开启时只记录 master 每次常驻保护叫停（类型、是否目标、回复调用数），不记录参数。

## 10. 用户决定：长时任务不设每回合调用数上限；连续相同调用保护保留（2026-10-02）

- **每回合调用数上限**：用户判断长时任务不需要调用次数上限。新增开关 `inference.tool_call_cap`，取值 `native_default`（默认，原生设置里完全不写 `model.maxToolCallsPerTurn`，保持原生自适应规则）或 `disabled`（写入 `0`，原生按无穷大处理）。两臂共用同一个值，Single、master、worker 一起生效。原生只看这个键在不在，存在就算显式设置，`null` 会被解析成硬上限 100，所以计划里禁止写 `null`、`0` 或其他数字，只接受这两个模式字符串。
- **背景数据**：P1 的 Single 3 小时 41 分时已有 418 次逻辑调用（约 113 次/小时），P0 的 Single 6 小时 422 次（约 70 次/小时），两次配置相同。按 P1 的速度跑满 6 小时约 660–680 次请求，若平均每次请求超过约 1.5 个工具调用，就会撞上原生默认的 1000 次上限，而且 Single 整个任务只有一个回合。显式 1000 只去掉"累计重复 6 次"那条，解决不了这个问题。
- **连续 5 次相同调用、Git 概览查看停滞**：保留原生行为，不改源码，只在披露里说明（需开启 `runtime_disclosure`）。理由：对 worker 来说，这是把"悄悄卡死"变成可见失败、让 master 能换人的唯一手段；两臂规则保持一致。
- **披露按模式生成**：`disabled` 时三个角色都写"一个回合内的工具调用次数没有上限"，不再出现 100/6/1000；Single 不再写"计数贯穿全任务"。默认模式下的文字不变。
- **记录**：`launch.json` 写 `tool_call_cap` 与 `native_max_tool_calls_per_turn`（键不存在时为 `null`），并加入 adaptations；`compatibility_loaded` 记录请求的模式；投影 `runtime_rules.effective.tool_call_cap`，旧运行记 `unknown`。原生的 `LoopDetectionService` 没有导出，没有逐角色读取实际生效值；改由下面的真实 CLI 测试证明设置作用于各角色。
- **代价（已告知用户）**：交替式死循环（例如 A、B 反复）不再被计数拦下，只能等 6 小时时限；这些运行本来也没有模型调用次数上限。
- **本地验证（真实 CLI＋脚本模型）**：单个回合约 120 次调用、同一命令每 4 次重复一次（不连续）。默认模式下，Single 和 worker 都在第 101 次调用时被 `turn_tool_call_cap` 叫停（Single 整个运行结束；worker 判 failed，master 收到失败通知）；`disabled` 下两者都跑完 120 次，正常收尾；关闭上限后，master 连续 5 次读状态文件仍被拦下。Linux 容器脚本已加上这 4 个场景，尚未运行。
- 未做：逐角色的计数观测（第 5.3 节）。
